## After the deadline

**First, if the documentation session finishes in time** (owner, 2026-11-24): the two bugs below, before the deadline.

- **The tab title reads the dictionary before it loads** (found in the review of the cleanup merge, which brought frontend ticket 37). Every page load logs `ERROR Error: The startup dictionary has not finished loading.` in the console: the effect in `PageTitleStrategy` reads `LanguageStore.text()` before the startup dictionary arrives, and `LanguageStore.selection()` throws. The title corrects itself once the dictionary lands (checked in English and Georgian), so only the console shows it. The unit tests miss it because `src/test-setup.ts` supplies the English dictionary up front. Fix sketch: `LanguageStore` exposes a loaded signal, the title effect sets nothing until it holds, and a spec starts the store without a dictionary. No ticket yet.
- **Back from editing your own post loses the profile** (found by the owner, 2026-11-24). Profile → Posts → edit one of your own posts: the Back button does not work properly, and the only ways out are the feed or another page; nothing leads back to the profile. The cause is not looked at yet. The place to start is `edit-post-page.ts`, which replaces its history entry with the post page after a save (`replaceUrl`), and the post page's Back link. No ticket yet.
- **Dropped frontend tickets** (owner, 2026-11-24). F39 (save a photo from the viewer) and F40 (save a message's or post's photos together) are a new feature with no time left. F42 (a three-field date of birth replacing the browser date picker in register and both admin dialogs) is polish and waits. All three stay `ready-for-agent`.
- **Ticket 24 was not spec-reviewed** (owner, 2026-11-24, to save usage). It was looked at by eye over two rounds. A standards pass on its diff is the cheap one to run later.

- **A signed event can be replayed** (found in the review of n8n ticket 01, owner, 2026-11-24). The workflows check only that the signature matches the body; they ignore the envelope's `id` and `occurredAt`, so a captured request is accepted again (a replayed fifth report re-hides content an administrator restored). The traffic stays on the owner's machine (`127.0.0.1:5678`), so it waits. Fix sketch: the signature check also refuses an `occurredAt` older than a few minutes, and n8n remembers recent `id`s; ticket 15's resend must then send a fresh time. The signature comparison is a plain string equals, not constant time; fix it in the same change. No ticket yet.

- **The profile of a deactivated account** (found in frontend ticket 22). `GET api/users/{id}` and `PUT api/users/{id}` go through the `User` query filter, so the backend can neither read nor edit a deactivated account's bio and date of birth. The admin panel lists such an account (the admin list ignores the filter), greyed, and offers Restore and Delete only; to edit it, an administrator restores it first (owner, 2026-11-22). Whether an administrator should be able to read or edit a deactivated profile is a backend decision to discuss. No ticket yet.
- **Extract the tail of `save()`** (found in frontend ticket 17, owner, 2026-11-24). The same nine lines end `save()` in `register-page.ts`, `create-account-dialog.ts`, `edit-profile-dialog.ts` and `profile-settings.ts`: `isSubmitting.set(false)`, `userRefusalField`, `setServerErrors`, `applyFieldErrors`, `failureMessage.set`. Two forms accept a username or an email refusal, two only a username. One helper next to `userRefusalField`, which sets the error on the control only if the form has it, removes both variants. No ticket yet.
- **Georgian dates in Chrome** (found in frontend ticket 09). Desktop Chrome has no Georgian locale data, so `DateFormatter` falls back to English month names on the Georgian interface; the time zone is right. The fix is a locale polyfill (`@formatjs/intl-datetimeformat` with `ka` data) or our own Georgian month names. No ticket yet; the owner accepts the English dates until then. Also worth doing in spare time before the deadline.
- **A presence race on a page reload** (found in frontend ticket 21, owner, 2026-11-24). A reload closes the old hub connection and opens a new one; if `OnDisconnectedAsync`'s offline write (`LastOnlineAt = now`) lands after `OnConnectedAsync`'s online write (`null`), the user stays "offline" while connected until their next reconnect (the `UserOffline` event also arrives after `UserOnline`). It needs the two writes to cross within milliseconds, and the cost is a wrong grey dot, so it waits. Fix sketch: `PresenceService.NotifyUserOfflineAsync` stamps and announces the departure only if `UserConnectionTracker` still has no connection for the user when the write runs; a test needs the two calls forced into that order.
- **A user's token sent with the automation's key** (found in n8n ticket 03, owner, 2026-11-24). On the two moderation routes such a request runs as the automation (raise only), but its `Log` row carries the user's id and no `Automation:` in `Details`, because `DatabaseLogger.LogUserActionAsync` checks for the automation only when there is no user id. Not a security gap (the sender already holds the key) and n8n never sends both. Fix sketch: the logger prefers the automation when `AutomationAuth.IsAutomation` holds, so the row has no user id and names the automation; a test sends both. No ticket yet.
- **Swagger shows enums as numbers** (found in n8n ticket 03, owner, 2026-11-24). The example bodies of the moderation route (`status`) and the report decision (`decision`) say `1`, but the API reads names only (`ModerationStatusJsonConverter`, `ReportDecisionJsonConverter`), so the example as sent gets `400`. Swashbuckle does not see converters set on a property. Fix sketch: a Swagger schema filter that lists these enums by name, which changes no API answer; a global `JsonStringEnumConverter` would also do it, but turns every enum the API now returns as a number into a name, which the frontend would have to be checked against. Development only. No ticket yet.

- **A smoother delete** (found in frontend ticket 21, owner, 2026-11-24). A deleted post, comment or message fades out over 200 ms (`FadeOut`, `DeleteFade`) and then leaves the list at once, so the items below jump up by its height. The likely fix, not yet tried: close the item's height while it fades (a grid row from `1fr` to `0fr`, or a measured `max-height`), so the list closes smoothly; it needs the 200 ms rule in `DESIGN.md` looked at, and a look at all four places that use `FadeOut` (post, comment, message, friend's row).
- **EF query weak spots** (found in a backend performance review, owner, 2026-11-25). Fine at the demo's size; each grows with the data. Worst first:
  - **The feed scores every post on every request.** `RankedFeedPageSql` in `PostRepository` counts likes and comments and computes the age of every candidate post, then sorts them all to return one page. Fix sketch: limit candidates to a recent window (for example 30 days, with older posts only past its end), or store a score refreshed by a background job.
  - **Paging without an order.** `UserRepository.SearchByUsernameAsync`, `UserRepository.GetNonConversationFriendsAsync` and `CommentRepository.GetByUserIdAsync` page with `Skip`/`Take` and no `OrderBy`, so SQL Server may repeat or skip rows between pages; `MessageRepository.GetConversationAsync` and `GetConversationFriendsAsync` order by time alone, with no `Id` tie-break. A correctness bug as well, each fix needs a paging test.
  - **Missing indexes** (one migration). `Logs.CreatedAt`: the fastest-growing table (a row per service call), sorted and filtered on it by the admin log search and the log cleanup. `Posts.ModerationStatus` and `Comments.ModerationStatus` for the moderation queue; `Messages (ReceiverUserId, Seen)` for unread counts.
  - **Reads are tracked by default.** `BaseRepository.Query(bool track = true)` makes comment lists, conversations and search pay for change tracking they never use. Fix sketch: the read-only list methods pass `track: false`; flipping the default instead needs every tracked caller found first.
  - Small: conversations include `ReceiverUser`, which nothing reads; `GetCommentWithCommenterUserAndPostById` includes `Post` twice; `PresenceService` sends one SignalR call per friend where `Clients.Groups(friendIds)` is one; username search is `LIKE '%x%'`, which no index helps (acceptable at this size). No ticket yet.
